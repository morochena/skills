# Skills comparison, 2026-10-24

## Decision

Keep the updated skills with one loop as the default and delegation available
for independent work. The results do **not** support a general speedup claim or
disabling workers across all workflows.

The maintenance update removed mandatory source-review workers, preserved the
tested quality, and substantially reduced reported token volume. Independent
utility implementation finished faster with workers than with workers disabled.
The updated ledger implementation profile was slower than the previous profile.
Choose the tradeoff for the task; worker count alone is not a performance metric.

After the evaluation, the agent-comparison reference gained an explicit check
for process exit versus actual task completion. Timings below refer to the
frozen initial skill update, before that final clarification.

## Comparison

Compared committed skills at `0993db05fb3758204406767f639639925f71d1c1` with
the proposed working-tree update. Each task used two repetitions per version,
with pair order reversed on repetition two. Trials ran sequentially in fresh
workspaces, using Codex CLI `0.163.0-alpha.11.2`, `gpt-6.1-sol`, and `xhigh`.
Parent and children used the same model and effort, confirmed from their logs.
Both versions had worker tools, capped at three children and one delegation level.
Every attempt had a five-minute wall-time limit and the same workspace-write sandbox.

There were **22 task attempts**: 16 usable paired attempts, two later no-worker
controls, and four initial verifier attempts excluded because their target was
protected from writes. Setup probes and the independent quality review are
outside the task timing and usage measurements.

The tasks were a SQLite transfer retry fix, three independent utilities,
maintenance of a real local CLI verifier, and assessment of supplied agent
benchmark evidence. This is a selected example suite, not a representative
software-development benchmark. It directly tests `do-work`,
`maintain-verification-skill`, and `benchmark-checklist`; it does not directly
benchmark `plan-work` or `improve-loop`.

## Independent-work control

Two additional utility attempts used the same frozen updated skill and task
with worker tools disabled. Both passed the behavioral checks.

| Updated utility configuration | Median seconds (range) | Median reported tokens |
| --- | --- | --- |
| Workers available; 3 and 2 actually used | 141.7 (135.4–147.9) | 616,652 |
| Worker tools disabled | 183.3 (168.6–198.0) | 175,614 |

The no-worker controls took 29.4% longer and used 71.5% fewer reported tokens.
They ran later and were not interleaved with the primary comparison, leaving
order, caching, and service-load confounds. They support preserving a delegation
exception, not a universal rule about which architecture is faster.

## Quality

- All eight paired coding attempts passed the external behavioral checks and
  their own final tests: seven external ledger checks and six utility checks
  per attempt. Both no-worker utility controls also passed. A supplementary
  5,000-digit integer probe passed across all six utility attempts; this probe
  is labeled post hoc in the evidence.
- All four corrected verifier attempts applied real edits, exercised every
  mapped feature, preserved evidence, removed scratch state, and left product
  code unchanged. An independent reviewer, blinded to version and outer
  performance metrics, awarded all four outputs 6/6 substantive criteria.
- All four read-only benchmark assessments met 9/9 rubric criteria in that
  blind review. Both versions caught the deliberately wrong source citation,
  supplied-finding leakage, missing usage, shared-budget failure, unstable
  fingerprints, and unsupported accuracy/cost/generalization claims. This case
  shows no observed quality gain from the added benchmark guidance.

The coding checks test outcomes, not instruction wording. The blind review
used source, corrected recipes, final answers, and captured CLI/command evidence.
These checks establish performance on the sampled contracts, not statistical
equivalence or complete correctness on arbitrary work.

## Harness corrections and evidence

The first verifier fixture lived under `.agents/skills`, a protected write
location in this sandbox. Three attempts returned blocked outcomes; one timed
out without a final answer. None applied the required changes. Those four
attempts remain recorded and are excluded from skill-performance conclusions.
Both versions were rerun twice using the explicitly configured
`verification/verify-taskdesk` root, after a real write/read-back preflight.
Sandbox permissions were unchanged. The grader now requires actual applied
feature corrections as well as live coverage.

The initial coding scope classifier also omitted related README changes. All
four ledger README changes were reviewed and found to document the requested
API/CLI behavior. Original automated flags remain in the evidence, alongside
the corrected scope review. No failed implementation check was discarded.

[The evidence bundle](2026-10-24-evidence.json) retains all 22 attempts, individual
measurements, per-session usage, original outcomes, scope review, fixture hashes,
frozen skill hashes and patch, control/correction protocols, blind ratings and
label mapping, and the review packet as inert text entries. It excludes
authentication and private runtime/account logs. Raw local execution artifacts
remain under `/tmp/skills-agent-loop-eval-20261024`.

Use the [harness instructions](../README.md) to reproduce a comparison. A later
run must select the intended baseline explicitly; model variability means it
will not reproduce these exact timings. This CLI experiment does not reproduce
Ultra Magnus's shared model-request budget or measure Phoenix implementation
quality, production rollout, larger repositories, or mixed-model delegation.
